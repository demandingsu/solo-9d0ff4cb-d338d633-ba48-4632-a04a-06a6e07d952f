# 环境监测小时观测数据平台

FastAPI + SQLite 的网页应用：测站结构（列名/列型）随时间演化，旧批次观测数据
仍可按**现役列名**统一查询，也可切回**历史版本**查看当时的列名与原始读数。
并支持把各区县**离线观测库的补录批次（单批 JSON）**迁入中心库：按稳定列标识
配对源字段，预览读数与校验错误后入库，同库同号幂等、换版须重新预览。

## 功能

- **发布初版结构**：自定义站号列、UTC 小时列与数据列（整数 / 小数 / 文本）。
- **按现役结构上传 CSV**：表头须与现役结构一致（顺序不限），逐行校验类型，
  任何一行不合格则**整批拒绝**，不产生半成品批次。
- **结构演化（发布新版本）**，只允许三类安全变更：
  - 改列名（含站号/小时列，跨多版连续改名也能找回旧值）；
  - 新增**可空**列（旧批次该行显示空值）；
  - 整数列**扩型**为小数列（旧值原样保留，不做任何换算）。
- **拒绝并回滚**：删除旧列、两列合并、一列拆多列、缩型（小数→整数等）、
  改系统列类型、新增非空列、列名重复——全部拒绝，现役版本与供数不受影响。
- **统一查询**：按站号 + UTC 小时区间查询，所有批次用现役列名展示。
- **历史视角**：选择任一历史版本，只看该版批次，列名与读数都是当时的样子。
- **交错安全**：发布 / 上传 / 查询均在全局锁 + 单事务内完成，结构与数据不混用。

### 离线库补录批次导入（单批 JSON）

- **文档格式**：顶层含 `source_library`（源库号）、`source_batch`（源批次号）、
  `fields`（字段编号 `field_id` 与名称 `field_name`），每行 `rows[]` 含
  `station`（站号）、`hour_utc`（UTC 小时）、`readings`（按字段编号记录的读数）。
- **两阶段网页流程**：先上传 JSON 拿到源字段清单与现役数据列，档案员把源字段
  按稳定列标识（`column_id`）配到**不同的现役数据列**（站号/小时为系统列不参与
  配对；未配对的源字段不导入）；再生成预览，逐行展示读数与校验错误。
- **首次入库只采用预览时的文件与配对**：预览行钉住原始文件文本、配对与当时的
  现役版本；确认入库时若现役结构已换版则拒绝并要求重新预览。
- **同库同号幂等**：同一源库的同号文件原样重传（SHA-256 相同）直接返回原入库
  批次号；内容有变一律拒收（HTTP 409）。不同源库各自编号、互不影响。
- **无半成品**：含校验错误的预览不能入库；入库在单事务内写入批次与全部读数，
  任一步失败整体回滚。
- **可追溯**：入库读数进入同一观测表，观测页与批次列表展示源库号、源批次号，
  并按现役列名统一查询（改名/加列/扩型规则同样适用）。

## 快速开始（Docker Compose）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据保存在命名卷 `obs-data` 中（容器内 `/srv/data/obs.db`）。

## 本地开发

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
# 打开 http://127.0.0.1:8000
```

## 页面操作流程（可用 examples/ 下的样例 CSV）

1. 「② 发布结构版本」发布初版：站号=`站号`，小时=`UTC小时`，数据列 `气温`(整数)、`气压`(整数)。
2. 「③ 上传」选择 `examples/v1_初版结构.csv`。
3. 「②」把 `气温` 改名为 `气温_C`、`站号` 改名为 `station_code`、`气压` 扩型为小数 → 发布 v2；上传 `examples/v2_改名扩型后.csv`。
4. 「②」把 `气温_C` 改名为 `温度`，新增可空列 `湿度`(整数) → 发布 v3；上传 `examples/v3_再加列后.csv`。
5. 「⑤ 查询」现役视角：v1 批次的 `温度` 列仍显示当年的 5/6/3，`湿度` 显示空值，`气压` 仍是整数 1013/1012/1015。
6. 「⑥ 版本历史」点 v1「以此视角查询」：只看到 v1 批次，列名是 `站号/气温/气压`，读数原样。

## 补录 JSON 导入流程（examples/ 下两个源库的同号样例）

样例 `import_QX-DONGHAI_B-007.json` 与 `import_QX-XISHAN_B-007.json` 来自两个不同
源库、源批次号同为 `B-007`；另有 `import_B-008_with_errors.json` 含各类校验错误。

1. 「②」发布含数据列 `气温`、`气压` 的初版结构。
2. 「④ 离线库补录批次导入」选择 `import_QX-DONGHAI_B-007.json`，点「上传并配对」：
   把 `f-temp→气温`、`f-pres→气压`（`f-wind` 可留“不导入”），点「生成预览」。
3. 预览逐行展示读数（含规范化后的 UTC 小时）；确认无误后点「确认入库」。
4. 原样重传同一文件：直接提示原入库批次号；把文件改一个读数再传：409 拒收。
5. 换西山库的同号样例重复 2–3：两个源库的同号批次各自独立、生成不同中心批次号。
6. 打开错误样例：预览列出坏小时、类型不符、空站号、未知字段编号等错误，且不出现
   入库按钮；强行调用入库接口返回 400，批次与读数数量不变。
7. 先对一个新批次生成预览但不入库，「②」发布换版结构后再点入库：提示须重新预览；
   重新预览并入库后，读数按新版列名出现在「⑤ 查询」。
8. 「⑤ 查询」与「⑦ 批次列表」中可看到每个补录批次的源库号、源批次号。

补录 JSON 文档示例：

```json
{
  "source_library": "QX-DONGHAI",
  "source_batch": "B-007",
  "fields": [
    {"field_id": "f-temp", "field_name": "气温(离线)"},
    {"field_id": "f-pres", "field_name": "本站气压(离线)"}
  ],
  "rows": [
    {"station": "S01", "hour_utc": "2026-11-18T00:00",
     "readings": {"f-temp": 5, "f-pres": 1013}}
  ]
}
```

## API 一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/versions` | 全部版本（含列定义） |
| GET | `/api/versions/current` | 现役版本 |
| GET | `/api/versions/{no}` | 指定版本 |
| POST | `/api/versions` | 发布新版本（初版或演化），非法变更 400 |
| POST | `/api/batches` | 上传 CSV（multipart，字段名 `file`），校验失败 400 且整批回滚 |
| GET | `/api/batches` | 批次列表（补录批次含 `source_library` / `source_batch`） |
| POST | `/api/imports/preview` | 补录 JSON 预览（multipart：`file`，可选 `mapping`）。无 `mapping` 返回配对表；带 `mapping` 钉住预览快照。同号原样重传 200 返回原批次号，内容变更 409 |
| POST | `/api/imports/{preview_id}/commit` | 按预览快照入库（201）；重复确认 200 幂等；换版后 400 要求重新预览 |
| GET | `/api/observations` | 查询：`station`、`hour_from`、`hour_to`、`version_no`（缺省=现役视角）、`limit`；每行含 `source_library` / `source_batch` |

`mapping` 为 JSON 字符串数组，每项 `{"field_id": "...", "column_id": "..."}`，
`column_id` 只能是现役数据列（站号/小时系统列不可作为目标），一个现役列至多被
一个源字段配对。

发布新版本请求体示例（演化）：

```json
{
  "note": "改名+扩型+加列",
  "columns": [
    {"source": "station", "name": "station_code"},
    {"source": "hour_utc", "name": "UTC小时"},
    {"source": "c1", "name": "温度"},
    {"source": "c2", "name": "气压", "type": "float"},
    {"source": null, "name": "湿度", "type": "integer", "nullable": true}
  ]
}
```

初版用 `{"role": "station"/"hour"/"data", "name": ..., "type": ...}` 声明列。

## 设计说明

- **列血缘**：每个逻辑列有稳定标识 `column_id`（`station` / `hour_utc` / `c1` / `c2` …）。
  改名、扩型复用同一 `column_id`，因此改名链跨多版仍可定位旧值。
- **原值存储**：观测值按上传时的解析结果存入 `observations.values_json`
  （`{column_id: value}`），之后任何版本操作都不改写它。新增列在旧行自然为空；
  扩型不回填（旧整数仍是整数，数值不变）。
- **事务与锁**：所有读写经 `db.session()`（全局 RLock + 单连接事务）。
  发布/上传先完整校验再写入，失败整体回滚——失败操作后仍按原版本供数。
- **小时规范化**：`2026-11-18 03:00`、`2026-11-18T03:00:00Z` 等写法统一规范为
  `YYYY-MM-DDTHH:MM` 存储，区间查询按字典序比较（规范后等价于时间序）。
- **补录导入的幂等与快照**：文件内容取 SHA-256 摘要，`(source_library,
  source_batch)` 在 `batches` 上有部分唯一索引（仅约束补录批次，CSV 直传批次
  三列为 NULL 不受影响）。预览写入 `import_previews` 表，钉住原始文件文本、
  配对 JSON 与 `version_id`；commit 时先核对现役版本未换版，再从快照重新解析
  并完整校验，全部通过后才在单事务内插入批次与读数并回写预览状态，失败整体回滚。
- **JSON 读数类型**：按目标现役列类型校验（整数列只接受 JSON 整数、小数列接受
  整数/有限浮点、文本列只接受字符串），JSON 布尔值一律拒绝；整数读数进入小数列
  时保留整数形态，与 CSV 通道行为一致。

## 已知限制

- 单进程 + SQLite，适合单站/小团队部署；多实例水平扩展需换外部数据库。
- 历史视角只显示该版本上传的批次（“当时的列名与当时的读数”），不把新批次映射进旧结构。
- 小时列按整点/分钟对齐，秒级或非 ISO 写法会被拒绝。
- 补录预览不做自动清理，`import_previews` 会持续累积（含未确认的 open 预览，
  仅占空间、不影响供数）；大批量使用时需要另加定期清理任务。
- 补录 JSON 与 CSV 上传均限制 20MB；超大批次需拆分文件。
